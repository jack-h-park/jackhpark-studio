# Vercel usage recovery retrospective

Through November 22, 2026. This is a historical record for Studio, with the
observed Production release at PR #263 (`b3b7f2d`) as the endpoint. Use the
[reset audit prompt](./vercel-usage-reset-audit-prompt.md) to independently
check current code, deployments, and measurements.

The strongest verified improvements were fewer scheduled probe requests,
smaller browser image transfers, and less work in specific local CPU fixtures.
Production deployment and sitemap verification explained most of the large ISR
write swings in the measured periods. Ordinary CPU reductions were inconsistent,
and the team was still above its 4-hour allowance at the last verified team
snapshot. The latest settings-computation optimization is local only.

## Remaining cost and how to investigate it

- **Repeated settings origin reads.** In the nine post-#263 hours after the first hour, all 35 recurring smoke requests to `/api/chat-runtime` were CDN MISS. The 60-second TTL is shorter than polling. The held patch avoids repeated computation after rereading the row. Avoid extending the failure freshness window or bypassing persisted settings without validating successful and failed invalidation, concurrent saves, and late cache fills.
- **Regional chat cache turnover.** In those same nine hours, smoke had 34 `/chat` STALE responses in `sfo1`, with a 16-minute median interval, and one HIT in `iad1`. Checkly in `iad1` logged 17 HIT, 17 MISS and 2 STALE with a 15-minute median interval. The shell has a 900-second TTL and 60-second stale-while-revalidate window. Smoke asserts status and title; Checkly asserts status and follows redirects. They overlap by path but cover different failure modes and mostly different CDN regions. Probe counts and cache statuses do not establish billed CPU per probe.
- **Hourly ISR and traffic mix.** In the first post-#263 hour, crawler user agents accounted for ten prerender STALE/MISS requests and smoke for four. Those signals are consistent with expiry and warming. They do not identify who caused each write unit. Earlier Functions Observability identified dynamic Notion routes as a major CPU workload, with recurring social-image and chat SSR cold starts. Recheck real data, since some detail panels displayed demo data and their invocation totals differed from billing.
- **Work still worth measuring separately.** Distinguish build CPU, Fluid CPU, CDN transfer, image transformations, ISR writes and deployment/function storage. Separate cold initialization, persistent decode, normalization, SSR and response serialization with representative offline input. Inspect cron and maintenance windows separately. Retain telemetry initialization where removing it loses or misparents spans. The audit did not establish how much team CPU came from any one background task.

Use complete, equal-duration fixed windows, confirm the actual Production SHA and readiness, and exclude matching clock bands on both sides if a deployment or sweep confounds either period. Wait for Usage ingestion. Record requests and route mix as context alongside CPU and write units. Treat unavailable or paywalled data as missing, never zero. Keep any verification requests and scheduler changes separate from measurement. See the [reset audit prompt](./vercel-usage-reset-audit-prompt.md).
