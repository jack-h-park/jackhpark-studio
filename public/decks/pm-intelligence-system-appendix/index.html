Takeaway 1 (cont.) — Determinism at two levels

  • Layer 1 · Process — pm-engine enforces an invariant pipeline (S1 → S2 → Gate 1 → S3 → S4 → Gate 2 → S5 → Gate 3 → S6 → S7). LLM outputs vary; the structure containing them doesn't. Why — if the sequence changes per signal, no two runs are comparable, so no change can be attributed to anything.
  • Layer 2 · Logic — deterministic work stays in code: S1 (categorize), S5 (composite score), routing → code; S2/S3/S4/S6/S7 → LLM (judgment is the point). LLM variance can't leak into routing/scoring. Why — for stages needing no judgment, code isn't less variable than a model, it's zero-variance.
  • Why both layers — process determinism alone still lets the model pick routing; code routing alone, under a varying pipeline, feeds different inputs into the same formula. Layer 1 fixes what runs; Layer 2 fixes what is computed.

Read-mostly — when the dashboard may write

Observability stays read-only; a write path ships only if it satisfies all five:

01
A runtime override store — never a git file, never .env (deleting it rolls back).
02
Its own env flag + resolved profile home — a dev checkout can't write; route 503s.
03
Atomic write (tmp-then-rename) — a cron reader never sees a half-written store.
04
A reader that degrades to the baseline when the store is missing/malformed.
05
Logged to the action log.
  • Today: sensing config · interview-drill TTS · gate actions · signal annotations · backup trigger · usage collector. Excluded: profile tuning:, path contracts, credentials, notification routing.
  • The rule behind all five: a settings bug must cost the setting — not the job.

Cross-cutting engineering principles

  • Eval-first — a harness of 4 regression fixtures from historical runs (R04–R07) predates the feature code; every prompt or model change is checked against it. They pin past behaviour, not validated ground truth — the calibration target going forward is accumulated Gate decisions.
  • Vendor-agnostic LLM — LLMProvider protocol → swap Claude / GPT via one env var.
  • Fail-closed security — no token ⇒ 503; loopback bind + Tailscale.
  • SQLite-first, protocol-abstracted — a future Postgres migration stays mechanical.
  • Traceability by design — every stage output stored, every gate decision logged, every artifact linked to its run.

Takeaway 1 (cont.) — What the two layers buy

Ad-hoc PM analysis vs pm-engine (both layers):

  • Workflow: varies per situation → fixed, same stages every time.
  • Consistency: varies per run → structural guarantee + exact code paths.
  • Traceability: effort-dependent → built-in, every run is a record.
  • Evolvability: hard, no seams → easy, swap any stage independently.

Takeaway 2 — For a personal system, MCP wasn't necessary

  • REST / CLI was enough. MCP earns its keep with a large/evolving surface, external discovery, or multi-vendor composition — none of which I had.
  • Agent → engine = REST — fixed internal surface (28 endpoints, ~10 at v1), all consumers on-machine.
  • Agent → publisher = CLI as a deliberate wall — internal changes don't leak, approval rules can't be bypassed, tokens never reach the agent.
  • Not the official Notion MCP: it grants broad read/write and can't enforce my narrow, gated, production-only write semantics.

F2 · Why an LLM Wiki — not RAG, not a bespoke DB?

  • RAG re-derives at query time — nothing accumulates. The wiki compiles knowledge once and keeps it current.
  • Decisive factor: human-readable, human-editable, human-manageable — open any file in Obsidian, no embeddings DB / vector index / infra.
  • The LLM does the bookkeeping (cross-refs, summaries, filing); you own schema + curation. Decisions distill into frameworks/cases — the corpus compounds.
  • Karpathy quote (bookkeeping is the tedious part; LLMs don't get bored and can touch 15 files in one pass) — LLM Wiki gist.

F7 (cont.) · The sensing funnel

source-feed-scanner runs every 6h as four stages, three zero-LLM:

01
Detect — RSS / HN / Reddit / web-search → keyword gate → exact dedup.
02

F8 · Two design choices that keep the pipeline honest

  • Portfolio fan-out — one signal, one primary product. A platform signal can touch several Knox products; auto-running per product flooded the loop (~2.4× gate load) for the same judgment. Default: Triage picks one primary; others recorded as candidates, promoted by hand; a promoted product re-enters at S2 (reusing the primary's product-agnostic S1), never Gate 0.
  • The knowledge track — independent of the decision. Every signal leaves two tracks; any terminal run (even an archive) can carry reusable knowledge → wiki/concepts · frameworks. Eligibility is a durability/abstraction test, not which depth ran.
