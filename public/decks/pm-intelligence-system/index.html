PM Intelligence
System

Making my PM decisions consistent, reproducible, and AI-leverageable — a system that structures the full cycle from market signal to product decision.

Not a copilot that assists with PM work. A system that runs on the PM's thinking.

Background

Why I built this

Product management is a judgment profession. Yet most time goes to the work surrounding decisions — gathering, normalizing, formatting, filing.

Most AI tools address that surrounding work but leave the judgment architecture to chance. A chatbot can draft a PRD — it can't ensure you evaluate an opportunity the same way every time.

A PM already has a way of thinking. The problem: it lives implicitly, applied inconsistently, leaving no record.

What I built toward

My philosophy externalized → decisions that come out "more me than me."

Knowledge that accumulates in an AI-leverageable form — Markdown in Obsidian, not a bespoke DB.

An agent fleet that keeps learning my know-how and runs the system with me.

Deterministic routing

The LLM scores; code routes. Same inputs, same output — always.

Reflections

What building this actually taught me

Takeaway 01

The biggest lever isn't the model. It's wrapping the LLM in
two layers of determinism — a fixed pipeline outside, code over the model inside.

Layer 1 · ProcessA fixed, invariant pipelineEvery signal runs the same stages and gates — structural consistency the LLM can't perturb.
Layer 2 · LogicCode over LLM, in-stageS1 categorize · S5 composite · routing stay in code — model variance can't leak into scoring.
Wins three at once cost ↓ consistency ↑ performance ↑ Not “coding with AI” — scaffolding for it.
Takeaways 02–05

What else building this taught me

02MCP wasn't necessary

For ~10 fixed endpoints in one on-machine fleet, REST was enough — and a CLI to the publisher is a deliberate wall: isolation, gate enforcement, secret containment.

03Context is king

Best isolated through clearly separated agents — split by identity / persona / R&R, not just data. Specialization, not autonomy, is the real point.

04Claude Code = VibeOps

Dev + devops paired with the prod fleet — cross-repo in one session, local and remote, ops in natural language. Not vibecoding — VibeOps.

05Autonomy is the direction — not today's priority

Decisions are far more non-deterministic than code. Until this matures, human-in-the-loop is non-negotiable.

F1 · FAQ

Why six repos — one per intent

Three groups, six repos — each with a distinct role and change cadence. Coupling would force a code deploy on every prompt tweak.

Different change cadences

Code dev · PM judgment · continuous operation · ops config · automated weekly sync.

Clear ownership boundaries

Each repo owns one thing — run state / reasoning / knowledge / identity / sync.

Independent deploy & test

The engine ships without touching the wiki; prompts change without redeploying code.

Blast-radius control

A mistake in one layer doesn't cascade across all of them.

Underlying principle — vibecoding is a means, not the goal: don't code what doesn't need code. An LLM Wiki over a custom DB/RAG; REST / CLI / GUI only where each earns its place.

F2 / F2a · FAQ

Wiki operations — skills & data edge

An LLM Wiki gives ~90% of a bespoke RAG with near-zero infra — human-readable and agent-readable at once. Three skills keep it coherent.

/ingest

Distills a raw source into the right canonical page(s); extracts the pattern; flags review_needed when confidence is low.

/query

Routes a question community-first via the Graphify graph; falls back to direct read if coverage is low.

/lint

Scans every page against the CLAUDE.md schema — flags orphans, duplicates, stale cross-refs.

Human owns the raw layer + schema. LLM owns wiki content — only after review_needed clears.
Data edge · notion-cms-backup Weekly one-way mirror

A GitHub Actions job syncs Jack's Notion workspace → the wiki raw layer. Decouples live edits from agent reads → grounded, versioned knowledge.

Raw layer only — never touches canonical pages directly (human gate via /ingest). Runs headlessly; no iMac dependency.

F4 / F5 · FAQ

Why REST & CLI, not MCP

Engine → REST Small, fixed, internal

~10 endpoints, stable surface. All consumers in the same on-machine fleet — no external discovery, no multi-vendor composition.

MCP would add a separate process, a parallel schema, connection-state, extra auth — complexity with no gain.

Publisher → CLI wall A deliberate boundary
Isolation — internal code changes don't leak to the agent.
Gate enforcement — human-approval rules can't be bypassed.
Secret containment — Notion tokens never reach the agent.

The official Notion MCP grants broad read/write — it can't enforce my narrow, gated, production-only semantics.

MCP earns its keep with a large / evolving surface, external discovery, or multi-vendor composition — none of which I had.

F8 · FAQ

Two choices that keep the pipeline honest

Portfolio fan-out One signal, one primary product

A platform signal can touch several Knox products at once. Auto-running the full pipeline per product flooded the review loop — ~2.4× gate load — for the same underlying judgment.

So Triage picks one primary; the rest are recorded as candidates I promote by hand. A promoted product re-enters at S2 — reusing the product-agnostic S1, never back at Gate 0.

The knowledge track Independent of the decision

Every signal leaves two tracks. The decision track exports the outcome — PRD / kill / PoC — to the wiki.

The knowledge track is separate: any terminal run — even an archive — can still distill reusable PM / market knowledge into wiki/concepts · frameworks. Eligibility is a durability test, not which depth ran.

Both exist to stop the pipeline from doing more than the decision warrants — fewer redundant runs, but nothing learned is thrown away.

F6 · FAQ

Where LLMs are used

Two integration styles + repos with no LLM. S1 and the S5 composite score are deterministic — no model.

Pattern ①Hermes gateway profiles

8 profiles · 3-tier chain openai-codex → anthropic (Claude) → openai-api key. Model tracks workload: gpt-5.4-mini for automation (ops·local·eval·scratch), gpt-5.4 for conversational (avatar·interview-ops·publisher·writer).

Pattern ②App-embedded SDK

pm-intelligence-engine · ~9–10 calls per decide run, all temperature=0. S2·S3·S4×4·S5-classify·S6·S7 call the model; S1 and the S5 composite don't. Swap via LLM_PROVIDER.

No LLMStore · serve · observe

decision-context · wiki · observatory · control-plane — context delivery and state, no inference.

Vendor-agnosticOpenAI is the default. Claude (claude-sonnet-5 full-tier · claude-haiku-4-5 mini-tier) is Fallback 1 across every gateway profile and the engine's configured alternative — swapped through one provider protocol.
